1. Purpose and System Definition

1.1 What Alfred is

Alfred is an agentic software-delivery control plane and execution layer that governs AI coding assistants such as Claude Code and GitHub Copilot.

Alfred does not attempt to make an LLM intrinsically reliable.

Instead:

«LLMs are treated as fallible, untrusted actors. Alfred provides the deterministic control system around them.»

Alfred is responsible for controlling:

- workflow selection
- workflow sequencing
- persona identity
- persona capabilities
- tool access
- requirements/specification lifecycle
- acceptance criteria
- planning
- implementation
- test strategy
- verification
- independent review
- risk assessment
- concurrency
- file ownership
- task claims
- inter-agent coordination
- evidence
- release sequencing
- human approval
- auditability
- lessons/standards governance
- worktree isolation
- execution limits
- host integration

The LLM supplies reasoning and generated work.

Alfred controls what the LLM is allowed to do, when it is allowed to do it, what evidence it must produce, and whether the result can progress.

---

2. Core Design Principles

2.1 Deterministic control around probabilistic actors

The central architectural principle is:

LLM = untrusted reasoning actor
Alfred = deterministic governance + execution boundary

LLMs must never be the final authority for:

- workflow transitions
- tool permissions
- risk classification
- acceptance of their own work
- independent review
- security approval
- concurrency ownership
- release approval
- specification mutability
- human approval state

---

2.2 Static capability identity

Tool access is determined by persona identity, not by an LLM choosing its own tools at runtime.

Every graph node is bound to a persona.

Every persona has:

- immutable tool grant
- refusal list
- weighted self-scoring rubric
- model-cost tier
- charter
- duties
- calibration
- overruling rules

This prevents an agent from dynamically escalating its own capabilities.

5. Supported Execution Surfaces

Alfred supports four principal user surfaces.

5.1 AI host slash-command surface

Supported hosts include:

- Claude Code
- GitHub Copilot in VS Code
- GitHub Copilot CLI

The host starts:

alfred serve --mcp

over local stdio.

Generated host slash commands are deliberately thin.

For example:

.claude/commands/alfred-deliver.md

must contain only procedural invocation behavior.

It must not duplicate:

- charters
- standards
- acceptance criteria
- verification plans
- workflow logic

Those are dynamically served through MCP.

---

6. Direct CLI Surface

Users can invoke workflows directly:

alfred <workflow>

CLI workflows operate against the same ledger and deterministic engine.

The CLI does not become a second implementation of workflow logic.

---

7. Mission Control

Mission Control is the local operator interface.

It is backed by the local Alfred serve layer.

It allows humans to:

- monitor runs
- inspect tasks
- observe agents
- inspect reasoning timelines
- resolve gates
- inspect Epics
- inspect conflicts
- monitor worktrees
- approve blocked execution

12. The 13 Workflows

12.1 "triage"

Purpose:

Determine whether a request is:

- bug
- feature
- chore
- question

Determines:

- owning codebase
- readiness
- blockers
- recommended next workflow

Reads ticket:

- yes

Writes spec:

- no

Board:

- no

Ships:

- no

Mode:

- plan

---

12.2 "spike"

Purpose:

Investigate genuine implementation options.

Must:

- compare 2–4 real options
- recommend one
- identify what would falsify the recommendation
- identify risks

Must not implement.

Mode:

- plan

---

12.3 "groom"

Purpose:

Turn requirements into point-sized, testable stories.

Produces:

- acceptance criteria
- scope
- out-of-scope
- stories
- estimates

Authors specification.

Can touch board.

Mode:

- plan

---

12.4 "plan"

Purpose:

Turn the specification into an executable implementation plan.

Must include:

- ordered steps
- files to change
- proving tests
- real verification commands

Refines the specification.

Mode:

- plan

---

12.5 "develop"

Purpose:

Implement and verify locally.

Must:

- work in isolated worktree
- use test-first development
- run real verification

Must never:

- commit
- push
- open PR
- mutate tracker/board
- ship

Mode:

- auto

This is an extremely strong invariant:

«Committing or pushing from "develop" is an unforgivable failure.»

The develop prompt must not contain shipping procedures.

---

12.6 "deliver"

Purpose:

Full implementation-to-PR delivery.

Includes:

- implementation
- verification
- fresh independent review
- fixes
- PR creation
- ticket movement

It is the sole end-to-end implementation and PR shipping workflow.

Mode:

- auto

---

12.7 "test"

Purpose:

Design, write, and execute tests.

Focus:

- realistic failures
- boundary cases
- empty sets
- failure paths
- regression coverage

Mode:

- auto

---

12.8 "review"

Purpose:

Independent adversarial review.

Reviewer:

- reads diff/range
- does not read ticket
- does not edit
- does not use shell

Review is based on engineering merit and standards, not the author's explanation.

Mode:

- plan

---

12.9 "verify"

Purpose:

Judge every acceptance criterion against evidence.

Unlike review, verification:

- reads ticket
- reads acceptance criteria
- can interact with board
- maps each criterion to evidence

Failures are classified as:

1. real bug
2. incorrectly stated criterion
3. broken test environment

Mode:

- auto

---

12.10 "ship"

Purpose:

Advise and sequence release across repositories.

Must include:

- deployment order
- reasons
- pre-deploy snapshot
- verification commands
- rollback plan

Must never deploy itself.

Mode:

- plan

---

12.11 "explain"

Purpose:

Onboard a human to an unfamiliar subsystem.

Must explain:

- plain-language architecture
- exact data path
- named files/functions
- file responsibilities
- unsafe-looking-but-safe/unsafe areas

---

12.12 "retro"

Purpose:

Look back at delivery evidence.

Produces:

- evidence-backed findings
- proposed lessons

Cannot directly mutate active standards.

---

12.13 "onboard"

Purpose:

Learn a repository and establish repository-specific knowledge.

Writes:

.alfred/PLAYBOOK.md
.alfred/playbook.json

Must cover:

- stack
- architecture
- patterns
- standards
- testing
- branch conventions
- commit conventions
- open questions

---

13. Workflow Safety Invariants

13.1 Develop vs Deliver

"develop":

implement + test

"deliver":

implement + test + review + verify + PR

Develop has no shipping authority.

---

13.2 Ship vs Deliver

"ship" is advisory release sequencing.

"deliver" owns implementation and PR shipping.

---

13.3 Specification immutability

Only:

- "groom" authors
- "plan" refines

After entering:

- develop
- deliver
- review
- verify

the specification is frozen.

---

13.4 Blind review

Reviewer must not read the ticket.

This prevents confirmation bias.

---

13.5 Verification

Verification explicitly uses:

- ticket
- acceptance criteria
- evidence

---

13.6 Retro governance

Retro can propose lessons.

Only explicit human promotion makes lessons active.

---

13.7 Automatic prerequisites

Normal delivery may automatically execute:

onboard
→ triage
→ groom
→ plan
→ develop/deliver

A prerequisite is skipped only where acceptable evidence already exists, such as:

- fresh playbook
- approved specification

The system must explain why a prerequisite was skipped.

PathGuard

15.1 Read

Properties:

- line-numbered
- 1-based pagination
- maximum 256 KiB
- binary detection from first 8192 bytes
- maximum 2000 characters per line
- maximum 2000 lines

Every read is recorded through:

context.ts:markRead

---

15.2 Write

Rules:

- read-before-write
- existing file must have been read during current session
- returns unified diff

---

15.3 Edit

Rules:

- read-before-write
- CRLF normalized to LF
- exact match required
- rejects absent target
- rejects ambiguous target
- rejects no-op edits

---

15.4 Bash

Execution root:

project root

Timeout:

default: 120 seconds
hard maximum: 600 seconds

Uses cooperative "AbortSignal".

Output maximum:

30,000 characters

---

15.5 Glob

Excludes dotfiles by default.

---

15.6 Grep

Rules:

- lines clipped to 400 characters
- maximum 200 results
- excludes:
  - "node_modules"
  - ".git"
  - "dist"

---

15.7 Walk

Maximum:

20,000 entries

Also excludes standard generated/internal directories.

18. Six House Rules

House rules are compiled TypeScript in:

packages/kernel/src/standards.ts

They are included in every brief and must be byte-identical.

18.1 Quality

Require:

- boundary-checked inputs
- deliberate errors
- smallest whole fix
- existing precedent
- idiomatic implementation
- no dead code
- no stubs
- no TODO placeholders

---

18.2 Security

Never:

- hardcode secrets
- use unvalidated SQL
- concatenate shell commands unsafely
- concatenate paths unsafely
- log credentials

Require validation at boundaries.

---

18.3 Tests

No change without tests.

Tests must cover:

- happy path
- failure path
- edge cases

Commands must actually be executed before claiming success.

---

18.4 Comments

No explanatory comments unless:

- required by toolchain
- necessary to explain a genuine surprise

Validated by:

check-comments.mjs

---

18.5 Authorship

Commits and PRs must be attributed to the human user.

Must not add:

- AI co-author trailers
- generated-by footers

---

18.6 Interface

Every UI must support:

- empty
- loading
- partial
- error
- success

Use design tokens.

Animations require:

- normal animation
- reduced-motion fallback

23. Deterministic Risk Model

LLM self-assessment is not trusted as a risk mechanism.

Risk is calculated from actual repository changes.

Implementation:

packages/knowledge/src/risk.ts

Model:

riskScore = sigmoid(
    bias
    + Σ(weight × feature)
)

Where:

sigmoid(z) = 1 / (1 + e^-z)

---

24. Risk Constants

Bias:

-3.0

Lines:

2.5

Uses log-scaled diminishing returns.

Files:

1.5

Uses log-scaled diminishing returns.

Churn:

1.5

Coverage:

2.0

Sensitive files:

3.0

Sensitive contribution saturates after two matched sensitive globs.

33. Liveness Model

Agent is:

active      < 2 minutes
heartbeat   every 90 seconds

34. Hard Task Claims

Task claims use an operating-system-level mutex.

Implementation:

claimTask()

uses:

open(file, 'wx')

Retry backoff:

5ms → 640ms

Stale claim:

10 seconds

Constant:

LOCK_STALE_MS = 10000

This guarantees two agents cannot simultaneously acquire the same task claim.

Potentially unreliable.

Deterministic evidence

Examples:

- Git diff
- executed test output
- CI configuration
- acceptance criteria
- file state
- risk calculation
- worktree state
- ledger events

The latter must be preferred for progression decisions.

---

129. Acceptance Criteria as Contract

Acceptance criteria are not merely prompts.

They are the contract between:

- product intent
- implementation
- QA
- reviewer
- verification
- delivery

Every acceptance criterion must eventually map to evidence.

---

130. Definition of Ready

A story is considered ready for implementation only when the required information needed by the workflow exists, including as applicable:

- clear intent
- scope
- acceptance criteria
- out-of-scope boundaries
- ownership
- executable plan
- proving verification strategy

If repository evidence cannot answer an important requirement question, grooming must ask the user rather than inventing an answer.

---

131. Definition of Done

A deliverable is not considered done merely because code compiles.

For delivery, the effective completion contract includes:

- implementation complete
- tests added
- tests executed
- CI/toolchain gates green
- acceptance criteria verified
- independent review completed
- high-severity findings resolved
- required security checks passed
- required human gates approved
- correct branch/commit behavior
- PR created where applicable
- ticket updated where applicable
- artifacts/audit state recorded

For "develop", the definition deliberately stops before shipping.

For "ship", the definition is a release sequence/rollback plan rather than actual deployment.

---

132. Repository Playbook as Local Knowledge

The playbook is repository-specific knowledge.

It must capture:

- stack
- architecture
- conventions
- testing
- CI
- branch conventions
- commit conventions
- open questions

It should shape future briefs without becoming a hidden source of executable authority.

---

133. Lessons Governance

Lessons are not automatically promoted into standards.

Lifecycle:

retro proposes
      ↓
human reviews
      ↓
accept/reject
      ↓
accepted lesson
      ↓
future brief

This prevents an incorrect AI observation from silently becoming permanent policy.

---

134. Concurrency Governance

Concurrency has multiple levels:

Task ownership

Hard OS lock.

File intent

Soft advisory lock.

Directory conflict

Deterministic prediction.

Worktree

Physical isolation.

Epic child

Independent worktree + tool/environment containment.

This layered model prevents relying on a single optimistic coordination mechanism.

---

135. Failure Philosophy

Failures must be visible.

Alfred must not convert:

unknown

into:

success

Examples:

- failed command ≠ green
- missing evidence ≠ passed criterion
- reviewer unable to verify ≠ approved
- stale checkpoint ≠ valid approval
- ambiguous project ≠ guessed project
- failed PR creation ≠ delivered
- failed push ≠ successful shipping
- broken environment ≠ passing test

---

136. Human-in-the-Loop Boundaries

Humans are explicitly required where deterministic safety cannot establish sufficient confidence.

Examples:

- guarded risk
- exhausted arbitration
- ambiguous target
- dangerous command
- Epic outside automatic-start conditions
- gate requiring human approval
- genuine merge conflict
- release approval

Human involvement is therefore a designed control boundary, not an exception to the architecture.

---

137. State Machine Philosophy

Alfred is not fundamentally a chat orchestration system.

It is a:

«compiled, schema-validated, persona-bound, bounded state machine whose actors happen to be LLMs.»

This distinction is architectural.

The LLM does not determine:

"What happens next?"

The graph determines that.

The LLM produces the output required by the current node.

140. Architectural Non-Goals

Alfred core must not become:

- a cloud-hosted coordination server
- a database-backed daemon
- an unrestricted autonomous coding agent
- a second implementation of each host's workflow logic
- an LLM-controlled permission system
- an automatic deployment engine
- an uncontrolled self-learning standards engine
- a reviewer that can silently patch its own findings

---

141. Key Structural Invariants

The following are considered architecture-level invariants:

1. LLMs are untrusted.
2. Graphs determine execution.
3. Personas determine capability identity.
4. Tools enforce physical capability boundaries.
5. Specs become immutable after planning.
6. Review is independent of author context.
7. Verification is acceptance-criterion based.
8. Risk is deterministic.
9. Dangerous commands require human approval.
10. Work is physically isolated in worktrees.
11. Coordination uses append-only journals.
12. Task claims use OS-level locking.
13. File intents remain advisory.
14. Epics are bounded to eight concurrent workers.
15. Workers cannot commit or approve their own work.
16. Lessons require explicit promotion.
17. Alfred core requires no external network.
18. Host adapters remain thin.
19. All user-facing state has explicit empty/loading/partial/error/success handling.
20. All autonomous loops are bounded.
21. All completed workflows produce auditable summaries.
22. No generated Alfred content silently overwrites user-owned content.
23. Failed operations must remain distinguishable from successful operations.
24. Human approval is an explicit state transition.
25. Acceptance criteria must map to evidence before delivery is considered complete.

142. Known Reconciliation / Implementation Audit Items

The consolidated specification must preserve known areas where documentation and observed implementation need reconciliation.

142.1 Configuration command

Documentation describes:

alfred config set

Observed implementation indicated "setup.sh" writes:

.alfred/config.yaml

directly and the "alfred config set" command was not present.

Action: reconcile specification and implementation before claiming the command as implemented.

---

142.2 Tool naming

Persona grants refer conceptually to:

read
search
edit
shell
alfred

Concrete implementations are:

read
write
edit
bash
glob
grep
walk

The architecture should explicitly document the mapping:

search → glob/grep/walk composition
shell  → bash

rather than pretending there are separate unimplemented "search" or "shell" tools.

---

142.3 Worktree ownership

Standard chat worktrees are instructed through the generated brief rather than created by Alfred itself.

Epic background workers are the deliberate exception because they require programmatic isolated worktree creation.

---

142.4 Gate writes

Most workflow state flows through MCP.

Mission Control gate approval deliberately bypasses MCP because it is a human operator control path.

This is an intentional exception and must remain documented.

144. Final Architectural Principle

The defining property of Alfred is not that it gives an AI more autonomy.

It is that it gives AI bounded autonomy with deterministic accountability.

The intended model is:

                 HUMAN INTENT
                      │
                      ▼
              ┌───────────────┐
              │    ALFRED     │
              │               │
              │ deterministic │
              │ state machine │
              │               │
              │ capabilities  │
              │ evidence      │
              │ risk          │
              │ gates         │
              │ concurrency   │
              │ audit         │
              └───────┬───────┘
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
       LLM ACTOR             HUMAN OPERATOR
          │                       │
          │ reasoning             │
          │ implementation        │
          │ analysis              │
          ▼                       ▼
       EVIDENCE  ───────────→  APPROVAL
          │
          ▼
       NEXT GRAPH STATE

The AI can reason, investigate, write and propose.

Alfred decides what is structurally permitted, what evidence is required, what must be reviewed, what must be verified, what is risky, what requires human intervention, and whether the system is allowed to progress.

That is the core architectural identity of Alfred v1.2.0.
