# Test design techniques: what to use when

Every technique below works from the **specification**: the AC, contracts and the requirement.
None of them needs the code.

## Boundary-value analysis (BVA) + equivalence partitioning (EP)
- **Use for** numeric ranges, string lengths, collection sizes, dates, and amounts with precision.
- **Partitions:** below-min (invalid), the valid range, above-max (invalid), and type-invalid. For
  optional fields add `missing`. For nullable fields add `null`. Unknown nullability stays
  *unspecified* and becomes a gap.
- **Boundaries** (3-point): min−1, min, min+1, max−1, max, max+1, using the specified step
  (0.01 for money with 2 decimals, one day for dates).
- **Extras worth one case each:** empty, maximum length in multi-byte characters (this catches
  byte-versus-character bugs), a leap day, and the end of the month.
- **Values** are generated by `boundary_values.py`. The design states only partitions and limits.

| AC says | Partition spec |
|---|---|
| "Transfers between €0.01 and €10,000" | `amount: {type: number, min: 0.01, max: 10000, precision: 2, required: true}` |
| "Memo up to 140 characters, optional" | `memo: {type: string, min_length: 0, max_length: 140, required: false, nullable: ?}`, where nullable is a **gap** |

## Decision tables
- **Use when** several conditions together determine an outcome: discount rules, permissions, routing.
- Build the table with one column per rule, collapse the "don't care" cells, and write **one scenario
  per column**. An impossible column becomes a QUESTION ("can a guest have a loyalty tier?").

| Conditions / rules | R1 | R2 | R3 | R4 |
|---|---|---|---|---|
| Logged in | N | Y | Y | Y |
| Loyalty tier | – | none | silver | gold |
| **Outcome: discount** | 0% | 0% | 5% | 10% |

## State-transition testing
- **Use for** order, payment, story or account lifecycles, and anything with a status field.
- Draw states × events. Test **every valid transition once**, and **at least one invalid transition
  per state**: the expected outcome is a rejection with a specific error, and no state change.
- For workflows that must reach a terminal state, add one round trip (create → … → terminal).

## Pairwise / combinatorial testing
- **Use for** three or more independent parameters (browser × locale × currency × role).
- Generate with PICT (or `allpairspy`), and state the constraints ("JPY has no decimals").
- Record the pairs covered and which exhaustive combinations were intentionally dropped
  (as an ASSUMPTION with impact).

## Error guessing (checklist; each item must cite a reason)
- **Duplicates and idempotency:** a double submit, or a replayed webhook.
- **Concurrency:** two updates to the same record (expect optimistic locking or a 409).
- **Dependency failures:** timeout, 5xx, or a malformed upstream response. The expected outcome
  comes from an NFR or error AC; if there is none, raise a gap.
- **Empty and zero states:** no items, first-time user, an empty search result.
- **Authorization:** another tenant's ID, an expired session. Coordinate with the security-testing skills.
- **Hostile input:** injection or markup in free text. The expected outcome is "stored and echoed
  verbatim but escaped", or "rejected".

## Choosing the tier (hint for test-engineer)
| Proves | Lowest tier |
|---|---|
| Pure rule or calculation | unit |
| Validation message shown, button disabled | component/widget |
| Request/response shape between services | contract |
| Business flow in domain language, which stakeholders read | BDD |
| Cross-screen journey with real persistence | E2E (critical journeys only) |
